# EIP-712: Typed Structured Data Hashing and Signing

## 1. Overview

EIP-712 is a standard for hashing and signing **typed structured data** on Ethereum. It extends the set of signable messages from transactions and raw byte strings to include human-readable structured data, enabling wallets like MetaMask to display meaningful information to users before they sign.

```
Signable Messages = 𝕋 ∪ 𝔹⁸ⁿ ∪ 𝕊

𝕋   = Transactions          → RLP encoding
𝔹⁸ⁿ = Raw byte strings      → ERC-191 personal sign
𝕊   = Structured data       → EIP-712 (this standard)
```

---

## 2. Encoding Specification

### 2.1 Three Encoding Methods

| Type | Encoding | First Bytes |
|---|---|---|
| Transaction `𝕋` | `RLP_encode(transaction)` | `0xc0`–`0xf9` |
| Byte string `𝔹⁸ⁿ` | `"\x19Ethereum Signed Message:\n" ‖ len(message) ‖ message` | `0x19 0x45` |
| Structured data `𝕊` | `"\x19\x01" ‖ domainSeparator ‖ hashStruct(message)` | `0x19 0x01` |

**Properties:**

- **Deterministic** — each individual component produces a unique output for a unique input.
- **Injective** — the three cases always differ in the first byte, making it impossible for different message types to produce the same encoding. RLP-encoded transactions never start with `0x19`.

**ERC-191 compliance:** The EIP-712 encoding maps directly to ERC-191 where the version byte is `0x01`, the version-specific data is the 32-byte `domainSeparator`, and the data to sign is the 32-byte `hashStruct(message)`.

### 2.2 Type 1: Transaction Signing (𝕋) — RLP Encoding

Transactions are RLP-encoded, hashed, and signed by the sender's private key. This is handled natively by the EVM — no custom contract code is needed.

**Solidity — sending a raw signed transaction:**

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

/**
 * @title TransactionSigningDemo
 * @notice Demonstrates how transaction signing works under the hood.
 *         In practice, wallets (MetaMask, ethers.js) handle this automatically.
 *
 * Transaction encoding:
 *   encode(tx) = RLP_encode(nonce, gasPrice, gasLimit, to, value, data, chainId, 0, 0)
 *   digest     = keccak256(encode(tx))
 *   signature  = ECDSA.sign(digest, privateKey) → (v, r, s)
 *
 * The first byte of RLP encoding is NEVER 0x19,
 * which is how it's distinguished from the other two signing types.
 */
contract TransactionSigningDemo {
    event Executed(address indexed sender, address indexed to, uint256 value);

    /**
     * @notice Verify that a transaction was signed by a specific address.
     * @dev    In practice, ecrecover is used to recover the signer from tx signature.
     *         The EVM does this automatically for every transaction — msg.sender
     *         is the recovered signer. This function demonstrates the manual process.
     *
     * @param txHash    The keccak256 of the RLP-encoded transaction
     * @param v         Recovery identifier (27 or 28, or chainId*2 + 35/36 per EIP-155)
     * @param r         First 32 bytes of the ECDSA signature
     * @param s         Second 32 bytes of the ECDSA signature
     * @return signer   The address that signed the transaction
     */
    function recoverTransactionSigner(
        bytes32 txHash,
        uint8 v,
        bytes32 r,
        bytes32 s
    ) external pure returns (address signer) {
        signer = ecrecover(txHash, v, r, s);
        require(signer != address(0), "Invalid signature");
    }

    /// @notice Simple function to demonstrate a signed transaction execution
    function execute(address to, uint256 value) external payable {
        // msg.sender is automatically verified by the EVM
        // via ECDSA recovery from the transaction signature
        emit Executed(msg.sender, to, value);
    }
}
```

**JavaScript (ethers.js) — signing and sending a transaction:**

```javascript
const { ethers } = require("ethers");

async function signAndSendTransaction() {
    const provider = new ethers.JsonRpcProvider("http://localhost:8545");
    const wallet = new ethers.Wallet(PRIVATE_KEY, provider);

    // 1. Construct the transaction
    const tx = {
        to: "0xRecipientAddress...",
        value: ethers.parseEther("1.0"),
        gasLimit: 21000,
        nonce: await wallet.getNonce(),
        chainId: (await provider.getNetwork()).chainId,
    };

    // 2. Sign the transaction
    //    Internally: RLP_encode(tx) → keccak256 → ECDSA.sign(hash, privateKey)
    const signedTx = await wallet.signTransaction(tx);
    console.log("Signed TX (RLP encoded):", signedTx);
    // signedTx starts with 0x02 (EIP-1559) or 0xf8... (legacy)
    // NEVER starts with 0x19

    // 3. Broadcast
    const receipt = await provider.broadcastTransaction(signedTx);
    console.log("TX Hash:", receipt.hash);
}

// Manually inspect RLP encoding
function inspectRLPEncoding() {
    const tx = ethers.Transaction.from({
        to: "0x0000000000000000000000000000000000000001",
        value: 0,
        gasLimit: 21000,
        gasPrice: ethers.parseUnits("20", "gwei"),
        nonce: 0,
        chainId: 1,
    });

    const serialized = tx.unsignedSerialized;
    console.log("RLP encoded (unsigned):", serialized);
    console.log("First byte:", serialized.slice(0, 4));
    // Will be 0xed, 0xf8, etc. — NEVER 0x19
}
```

### 2.3 Type 2: Personal Sign (𝔹⁸ⁿ) — ERC-191

Personal sign prefixes the message with `"\x19Ethereum Signed Message:\n"` + length. This is what MetaMask shows when you click "Sign Message".

**Solidity — full contract with verification:**

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

import "@openzeppelin/contracts/utils/cryptography/ECDSA.sol";

/**
 * @title PersonalSignDemo
 * @notice Demonstrates ERC-191 personal_sign verification on-chain.
 *
 * Encoding:
 *   encode(message) = "\x19Ethereum Signed Message:\n" ‖ len(message) ‖ message
 *
 * The prefix byte is 0x19, second byte is 0x45 ('E'),
 * distinguishing it from transactions (0xc0-0xf9) and EIP-712 (0x19 0x01).
 */
contract PersonalSignDemo {
    using ECDSA for bytes32;

    mapping(address => bool) public verified;

    event SignatureVerified(address indexed signer, string message);

    /**
     * @notice Verify a personal_sign signature and mark the signer as verified.
     *
     * @dev How it works:
     *      1. Hash the raw message: messageHash = keccak256(message)
     *      2. Apply ERC-191 prefix: ethSignedHash = keccak256(
     *             "\x19Ethereum Signed Message:\n32" + messageHash
     *         )
     *      3. Recover signer: ECDSA.recover(ethSignedHash, signature)
     *
     *      The "32" in the prefix is because we're signing a 32-byte hash.
     *      If signing raw string "hello" directly, it would be "5".
     *
     * @param message    The original message that was signed
     * @param signature  65-byte ECDSA signature (r + s + v)
     * @return signer    The recovered signer address
     */
    function verifyAndMark(
        string calldata message,
        bytes calldata signature
    ) external returns (address signer) {
        // Step 1: Hash the message content
        bytes32 messageHash = keccak256(abi.encodePacked(message));

        // Step 2: Apply the Ethereum personal sign prefix
        // This recreates what MetaMask signed internally
        bytes32 ethSignedHash = MessageHashUtils.toEthSignedMessageHash(messageHash);

        // Step 3: Recover the signer from the signature
        signer = ECDSA.recover(ethSignedHash, signature);

        // Step 4: Application logic
        verified[signer] = true;
        emit SignatureVerified(signer, message);
    }

    /**
     * @notice Verify without state changes (view function)
     */
    function verifyOnly(
        string calldata message,
        bytes calldata signature
    ) external pure returns (address signer) {
        bytes32 messageHash = keccak256(abi.encodePacked(message));
        bytes32 ethSignedHash = MessageHashUtils.toEthSignedMessageHash(messageHash);
        signer = ECDSA.recover(ethSignedHash, signature);
    }

    /**
     * @notice Manual implementation showing exactly what happens inside the prefix
     * @dev    Equivalent to OpenZeppelin's toEthSignedMessageHash
     */
    function verifyManual(
        string calldata message,
        bytes calldata signature
    ) external pure returns (address signer) {
        bytes32 messageHash = keccak256(abi.encodePacked(message));

        // This is exactly what "\x19Ethereum Signed Message:\n32" does:
        //   0x19 = prefix byte (same as EIP-712, but next byte differs)
        //   "Ethereum Signed Message:\n" = literal string
        //   "32" = length of the hash in ASCII decimal (non-zero-padded)
        bytes32 ethSignedHash = keccak256(abi.encodePacked(
            "\x19Ethereum Signed Message:\n32",
            messageHash
        ));

        signer = ECDSA.recover(ethSignedHash, signature);
    }

    /**
     * @notice Verify a raw string signature (not pre-hashed)
     * @dev    When signing "hello" directly, the prefix uses "5" not "32"
     */
    function verifyRawString(
        string calldata message,
        bytes calldata signature
    ) external pure returns (address signer) {
        // For raw strings, length is the byte length of the message
        bytes32 ethSignedHash = keccak256(abi.encodePacked(
            "\x19Ethereum Signed Message:\n",
            Strings.toString(bytes(message).length),
            message
        ));

        signer = ECDSA.recover(ethSignedHash, signature);
    }
}
```

**JavaScript (ethers.js) — signing and verifying off-chain:**

```javascript
const { ethers } = require("ethers");

async function personalSignDemo() {
    const provider = new ethers.JsonRpcProvider("http://localhost:8545");
    const wallet = new ethers.Wallet(PRIVATE_KEY, provider);

    // ═══════════════════════════════════════════
    //  SIGNING (off-chain)
    // ═══════════════════════════════════════════

    const message = "Hello, Ethereum!";

    // Method 1: signMessage (applies ERC-191 prefix automatically)
    const signature = await wallet.signMessage(message);
    console.log("Message:", message);
    console.log("Signature:", signature);

    // ═══════════════════════════════════════════
    //  WHAT HAPPENS INTERNALLY
    // ═══════════════════════════════════════════

    // Step 1: Prefix the message
    //   "\x19Ethereum Signed Message:\n16Hello, Ethereum!"
    //   16 = byte length of "Hello, Ethereum!"
    const prefixed = ethers.concat([
        ethers.toUtf8Bytes("\x19Ethereum Signed Message:\n"),
        ethers.toUtf8Bytes(String(ethers.toUtf8Bytes(message).length)),
        ethers.toUtf8Bytes(message),
    ]);
    console.log("\nPrefixed message (hex):", ethers.hexlify(prefixed));
    console.log("First byte:", ethers.hexlify(prefixed.slice(0, 1)));
    // → 0x19 (distinguishes from RLP transactions)

    // Step 2: Hash the prefixed message
    const digest = ethers.keccak256(prefixed);
    console.log("Digest:", digest);

    // Step 3: ECDSA sign the digest
    // (wallet.signMessage does steps 1-3 in one call)

    // ═══════════════════════════════════════════
    //  VERIFICATION (off-chain)
    // ═══════════════════════════════════════════

    // Recover signer from signature
    const recoveredAddress = ethers.verifyMessage(message, signature);
    console.log("\nRecovered signer:", recoveredAddress);
    console.log("Matches wallet:  ", recoveredAddress === wallet.address);

    // ═══════════════════════════════════════════
    //  VERIFICATION (on-chain)
    // ═══════════════════════════════════════════

    // Deploy and call the contract
    const contract = await ethers.getContractAt("PersonalSignDemo", DEPLOYED_ADDRESS);

    // Pass the original message + signature
    // Contract will recreate the prefix and recover the signer
    const signer = await contract.verifyOnly(message, signature);
    console.log("\nOn-chain recovered signer:", signer);
}

// ═══════════════════════════════════════════
//  SIGNING A HASH (32 bytes) vs RAW STRING
// ═══════════════════════════════════════════

async function hashVsRawString() {
    const wallet = new ethers.Wallet(PRIVATE_KEY);

    // Signing a raw string "hello"
    // → prefix: "\x19Ethereum Signed Message:\n5hello"
    const sig1 = await wallet.signMessage("hello");

    // Signing a hash (32 bytes)
    // → prefix: "\x19Ethereum Signed Message:\n32" + hash
    const hash = ethers.keccak256(ethers.toUtf8Bytes("hello"));
    const sig2 = await wallet.signMessage(ethers.getBytes(hash));

    // These produce DIFFERENT signatures because the prefix length differs
    console.log("Raw string sig:", sig1);
    console.log("Hash sig:      ", sig2);
    console.log("Same?", sig1 === sig2); // false
}
```

## 3. Definition of Typed Structured Data `𝕊`

### 3.1 Type System

The EIP-712 type system is closely related to Solidity types but is designed to be EVM-specific and language-agnostic.

**Example struct:**

```solidity
struct Mail {
    address from;
    address to;
    string contents;
}
```

A **struct type** has a valid identifier as its name and contains zero or more member variables, each with a member type and a name.

### 3.2 Member Types

| Category | Types | Notes |
|---|---|---|
| **Atomic** | `bytes1`–`bytes32`, `uint8`–`uint256`, `int8`–`int256`, `bool`, `address` | No aliases (`uint`, `int`). No fixed-point. Contract addresses are plain `address`. |
| **Dynamic** | `bytes`, `string` | Same declaration as atomic types but different encoding treatment. |
| **Reference** | Arrays (`Type[n]`, `Type[]`), Structs | Structs are referenced by name. Recursive struct types are supported. |

The set `𝕊` contains all instances of all struct types.

---

## 4. Core Hash Functions

### 4.1 `hashStruct`

```
hashStruct(s : 𝕊) = keccak256(typeHash ‖ encodeData(s))

where typeHash = keccak256(encodeType(typeOf(s)))
```

The `typeHash` is a **compile-time constant** for a given struct type — no runtime computation needed.

### 4.2 `encodeType`

The type is encoded as a canonical string representation:

```
name ‖ "(" ‖ member₁ ‖ "," ‖ member₂ ‖ "," ‖ … ‖ memberₙ ‖ ")"
```

Each member is written as `type ‖ " " ‖ name`.

**Simple example:**

```
Mail(address from,address to,string contents)
```

**With referenced structs:** All referenced struct types are collected, sorted by name, and appended:

```
Transaction(Person from,Person to,Asset tx)Asset(address token,uint256 amount)Person(address wallet,string name)
```

**Solidity constant:**

```solidity
bytes32 constant MAIL_TYPEHASH = keccak256(
    "Mail(address from,address to,string contents)"
);
```

### 4.3 `encodeData`

The encoding of a struct instance is the concatenation of encoded member values in declaration order. Each encoded value is exactly **32 bytes**.

**Encoding rules by type:**

| Type | Encoding Rule |
|---|---|
| `bool` | `false` → `uint256(0)`, `true` → `uint256(1)` |
| `address` | Encoded as `uint160` |
| `intN` / `uintN` | Sign-extended to 256-bit, big-endian |
| `bytes1`–`bytes31` | Zero-padded at the end to `bytes32` |
| `bytes`, `string` | `keccak256` of their contents |
| `Type[]`, `Type[n]` | `keccak256` of concatenated `encodeData` of each element |
| Struct | Recursive `hashStruct(value)` — undefined for cyclical data |

**Solidity implementation:**

```solidity
function hashStruct(Mail memory mail) pure returns (bytes32 hash) {
    return keccak256(abi.encode(
        MAIL_TYPEHASH,
        mail.from,
        mail.to,
        keccak256(bytes(mail.contents))
    ));
}
```

**Gas-optimized in-place implementation:**

```solidity
function hashStruct(Mail memory mail) pure returns (bytes32 hash) {
    bytes32 typeHash = MAIL_TYPEHASH;
    bytes32 contentsHash = keccak256(bytes(mail.contents));

    assembly {
        let temp1 := mload(sub(mail, 32))
        let temp2 := mload(add(mail, 128))

        mstore(sub(mail, 32), typeHash)
        mstore(add(mail, 64), contentsHash)

        hash := keccak256(sub(mail, 32), 128)

        mstore(sub(mail, 32), temp1)
        mstore(add(mail, 64), temp2)
    }
}
```

This assumes structs are not allocated below address 32, members are stored in order, all values are padded to 32-byte boundaries, and dynamic/reference types are stored as 32-byte pointers.

## 5. Domain Separator

### 5.1 Definition

```
domainSeparator = hashStruct(eip712Domain)
```

The `EIP712Domain` struct uses one or more of the following fields. Unused fields are omitted from the struct type entirely.

### 5.2 Fields

| Field | Type | Purpose |
|---|---|---|
| `name` | `string` | Human-readable name of the signing domain (dApp or protocol name) |
| `version` | `string` | Current major version of the signing domain. Different versions are incompatible. |
| `chainId` | `uint256` | EIP-155 chain ID. Wallets should refuse signing if it doesn't match the active chain. |
| `verifyingContract` | `address` | Address of the contract that will verify the signature. Enables contract-specific phishing prevention. |
| `salt` | `bytes32` | Disambiguating salt as a last-resort domain separator. |

**Field ordering:** Fields should follow the order listed above, skipping any absent fields. Future additions must be in alphabetical order and come after the existing fields. Wallets should accept fields in any order as specified by the `EIP712Domain` type.

### 5.3 Purpose

The domain separator serves two critical functions:

1. **Prevents cross-dApp collision** — Two dApps with identical struct types (e.g., `Transfer(address from, address to, uint256 amount)`) produce different signatures because their domain separators differ.

2. **Enables multiple signature use-cases within one dApp** — For example, a transfer might require signatures from both `from` and `to`. Different domain separators can distinguish these.

## 6. JSON-RPC API

### 6.1 `eth_signTypedData`

Calculates an Ethereum-specific signature:

```
sign(keccak256("\x19\x01" ‖ domainSeparator ‖ hashStruct(message)))
```

**Parameters:**

| # | Type | Description |
|---|---|---|
| 1 | `address` | 20 bytes — account address (must be unlocked) |
| 2 | `TypedData` | JSON object containing type info, domain params, and message |

**TypedData JSON Schema:**

```json
{
  "types": {
    "EIP712Domain": [
      { "name": "name", "type": "string" },
      { "name": "version", "type": "string" },
      { "name": "chainId", "type": "uint256" },
      { "name": "verifyingContract", "type": "address" }
    ],
    "Person": [
      { "name": "name", "type": "string" },
      { "name": "wallet", "type": "address" }
    ],
    "Mail": [
      { "name": "from", "type": "Person" },
      { "name": "to", "type": "Person" },
      { "name": "contents", "type": "string" }
    ]
  },
  "primaryType": "Mail",
  "domain": {
    "name": "Ether Mail",
    "version": "1",
    "chainId": 1,
    "verifyingContract": "0xCcCCccccCCCCcCCCCCCcCcCccCcCCCcCcccccccC"
  },
  "message": {
    "from": { "name": "Cow", "wallet": "0xCD2a3d9F938E13CD947Ec05AbC7FE734Df8DD826" },
    "to": { "name": "Bob", "wallet": "0xbBbBBBBbbBBBbbbBbbBbbbbBBbBbbbbBbBbbBBbB" },

  }
}
```

**Returns:** `DATA` — 65-byte hex-encoded signature (`0x` prefix). Bytes 0–31 contain `r`, bytes 32–63 contain `s`, and the last byte contains `v` (includes chain ID per EIP-155).

## 8. Design Rationale

### 8.1 Why the `\x19\x01` Prefix?

The first byte distinguishes signing cases. Starting directly with the domain separator or typeHash is unsafe — it may be possible to construct a typeHash that happens to be a valid prefix of an RLP-encoded transaction.

### 8.2 Why Domain Separators?

Without domain separators, two dApps with identical struct types would produce identical signatures. The domain separator guarantees no signature collision between different protocols or between different use-cases within the same protocol.

**Alternative considered:** Using the target contract address alone. This solves cross-contract collision but doesn't support multiple signing contexts within a single dApp.

### 8.3 Why typeHash in hashStruct?

The typeHash separates types so that `encodeData` only needs to be injective within a given type. It's acceptable for `encodeData(a) == encodeData(b)` as long as `typeOf(a) != typeOf(b)`.

**Alternatives considered and rejected:**

| Alternative | Reason for Rejection |
|---|---|
| ABIv2 4-byte function signatures | Not collision-resistant (only `bytes4`) |
| 256-bit ABIv2 signatures | Doesn't capture semantics — causes collisions like ERC-20 vs ERC-721 `transfer(address,uint256)` |
| 256-bit ABIv2 + parameter/struct names | String length can grow exponentially; doesn't support recursive types |
| Include NatSpec documentation | Makes documentation changes breaking; too verbose |

### 8.4 Why This encodeData Design?

**Alternatives considered and rejected:**

| Alternative | Reason for Rejection |
|---|---|
| Tight packing | Requires complex EVM packing instructions; no in-place computation |
| ABIv2 encoding | Not deterministic (multiple valid encodings for same data); no in-place computation |
| Omit typeHash from hashStruct | Breaks injectivity of keccak256 semantics |
| Support cyclical data | Prohibitively complex; breaks composability of member hashes |

### 8.5 Directed Acyclic Graphs

A simple recursive implementation can visit the same node twice in DAGs. Memoization can optimize this but is not required by the standard.

## 9. Security Considerations

### 9.1 Replay Attacks

EIP-712 only specifies signing and verification — it does **not** handle replay protection. Applications must implement their own:

- **Nonce tracking** — reject previously-used nonces
- **Idempotent actions** — ensure repeated execution produces the same effect
- **Deadline enforcement** — reject expired signatures

### 9.2 Frontrunning Attacks

The broadcast mechanism is application-specific. When signatures are submitted to a blockchain, attackers can intercept and submit them first. Applications must handle this by either rejecting front-run submissions or ensuring the same effect regardless of who submits.

### 9.3 Replay Protection Summary

| Attack Vector | Mitigation |
|---|---|
| Cross-chain replay | `chainId` in domain separator |
| Cross-contract replay | `verifyingContract` in domain separator |
| Cross-version replay | `version` in domain separator |
| Same-message replay | Per-user nonce counter (application-level) |
| Expired intent | `deadline` field in signed struct |

---

## 10. Backwards Compatibility

- The RPC calls, Web3 methods, and `SomeStruct.typeHash` are previously undefined — defining them does not affect existing dApps.
- The Solidity expression `keccak256(someInstance)` for a struct instance currently evaluates to the keccak256 of the **memory address**, not the struct contents. This behavior is dangerous and non-deterministic. DApps relying on it should be considered broken.

## 11. Complete Signing Flow

```
                                    OFF-CHAIN
┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│  1. Define types                                                │
│     types = { EIP712Domain: [...], Mail: [...], Person: [...] } │
│                                                                 │
│  2. Construct domain                                            │
│     domain = { name, version, chainId, verifyingContract }      │
│                                                                 │
│  3. Construct message                                           │
│     message = { from: {name, wallet}, to: {name, wallet},      │
│                 contents: "Hello, Bob!" }                       │
│                                                                 │
```
